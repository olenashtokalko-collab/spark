Consistency audit before the Storybook

What the approved Health version actually uses today: colours, type, corners, shadows and controls, measured from the running portal. Each finding names the drift and the one value to keep, so the Storybook starts from a single set of tokens and components.

What the portal uses today

Computed styles of every visible element on ten Health states: Home, the account menu, Requests, Documents, New request, Top up, Company profile, Ask Dr.AI, a chat and its history. Archived Home versions and demo pages are left out.

Most of the drift comes from layering: Health restyles older components by overriding them (often with !important on :root[data-theme][data-ui] body …), so each screen we tuned on review kept its own values.

Findings

Ranked by what a client would notice. P1 shows the same thing two ways on screen; P2 is drift in the type and colour scale; P3 is under the surface.

Status, 18 Nov: P1, P2 and P3 are applied on localhost in one layer, src/styles/health-system.css, with Top up rebuilt on Dialog. Added on review: an xs button size (32 px) and a white primary on dark surfaces.

From here to the Storybook

  1. Agree the keeps above.

    Mainly P1: one primary, one secondary, one status, one round icon button. The scales (greys, radii, type) follow from them.

  2. Write the Health tokens.

    One tokens file for colour, type, radius, shadow and spacing, used by Health's styles in place of the hand-picked values.

  3. Fold the components onto the tokens.

    Button, icon button, field, tabs, status, tag, card, modal, drawer, menu; Top up onto Dialog. The overrides that only fought older styles come out.

  4. Start the Storybook.

    Tokens first, then those components with their variants and states, each story rendered in Health's theme.

Measured on localhost from the prototype on the glass-variant branch. Counts are uses of each computed value across the ten states, so a value seen on several screens counts once per screen.
